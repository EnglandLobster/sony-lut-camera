# rc.7：A5100 / A6300 保存核验回归

## 与 PR #2 的关系

PR #2 固定 head `cdc0c54` 基于旧主线，修复的是 API10 `Canvas.setBitmap(null)` 动画清理异常。其具名保存路径直接使用 Sony 完成通知与 JPEG 头校验，不要求原片先进入索引。

我们在 `797af93`（rc.3）统一新旧保存协议时，给具名路径也加上了“完整 JPEG + 新增索引”的硬条件。rc.4 合并 PR 时带入该规则，rc.5 又改成先查索引。问题因此可能出现在合并版，而不是来自作者那段动画修复。PR 的原始贡献和清理修复全部保留。

## 现象、证据与推断

A5100 / 固件 3.10 的截图显示“正在等待照片与索引确认”，对应保存 RPC 已返回后的 UI 分支；用户描述之后关机再开机出现 Sony 原生写卡恢复提示。截图没有显示应用版本。

已有 A6300 两次成功实拍日志中的顺序：

| 事件 | 第一张拍摄 | 第二张拍摄 |
|---|---|---|
| 原片确认 | 00:03:49.780 | 00:04:00.603 |
| 提交调色片 | 00:03:49.783 | 00:04:00.605 |
| 调色片确认 | 00:03:50.880 | 00:04:01.697 |
| 索引更新通知 | 00:03:50.886 | 00:04:01.753 |

原流程预先声明 `EXPOSURE_COUNT=1, RECORD_COUNT=2`。如果索引要等整组完成才发布，新增硬条件就形成循环：原片等待索引，程序不提交第二张，索引又等第二张完成。索引更新通知在两张完成之后是已观察事实；不能仅凭通知时间认定每个固件的每次查询都延后。我们以该时序建立可执行模型：rc.6 在成功回调、RPC 返回、完整原片均存在的情况下，模拟时间 40 秒后仍 pending，无法提交第二张。该回归已本地复现。

原生恢复提示与中途关机打断未完成双记录事务相符，但这位用户缺少现场日志，尚未确定它唯一的底层触发点。

另已读取 A6300 2.01 的 `AvindexProvider`：`query` 调用 `checkDatabase`，内部检查 `needUpdate` 并执行 `updateDatabase`；因此没有把“缺少手动刷新”当作结论，也没有额外调用阻塞式 `waitAndUpdateDatabase`。

## 修复

- 具名成功回调、RPC 返回、稳定完整且尺寸正确的目标 JPEG 共同确认该记录，**不再强制索引可见**。失败状态不会当作成功，重复/旧回调仍不重复完成。
- 回调缺失才走独立索引恢复线程，队列至多一项在途查询；阻塞查询不能占住成功回调的处理线程。保存前索引快照最多等 1 秒，现代协议可继续等待原生回调；旧协议缺乏安全水位时在提交保存前明确失败。
- 索引恢复过滤已经由回调确认的 DCF 身份，允许两张记录一起晚入库；空索引水位改为 -1，避免丢掉合法的第一条序号 0。
- 停止/返回仍完成已经声明的双记录事务。确认原片后仅允许一个 `beginFinalStore`，完成后禁止第三条或新拍摄；不因计时结束释放仍由原生调用持有的图像。
- UI 和私有等待快照区分保存调用、回调、索引、文件验证及读取错误；记录实际查询次数/在途时间、原生状态码和最后错误原因链。

## LUT 扫描反馈

`LutLibrary` 从 PR head 到 rc.6 没有变化，原来只扫描根目录 `LUTS` 的直接 `.cube/.cub` 文件；用户文字提及 `lut` 文件夹。rc.7 增加 `LUT` / `LUTS` 目录别名与大小写兼容，保留直接文件、扩展名、路径边界和内容去重规则。没有据截图认定用户的实际文件名或扩展名。

- 已发布 rc.6 的循环等待模型复现；修复版通过四组批量索引发布场景（继续/停止 × 最终回调存在/丢失）。
- 实际阻塞线程：索引查询挂起、索引快照挂起、迟到回调完成双保存、禁止查询任务堆积；旧协议无水位时不提交保存。
- 18 组全尺寸/新旧协议、4 组保存 RPC 阻塞、跨进程保护、索引边界与动画 96 轮继续通过。

- 导入测试覆盖 `LUTS` 与小写单数 `lut`、子目录/双扩展名排除和符号链接边界。发行签名与内置 LUT 保持不变。
