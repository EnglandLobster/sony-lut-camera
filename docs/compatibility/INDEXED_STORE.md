# rc.5：保存确认顺序与 A7 写卡反馈

## 证据与修复范围

A7 / 固件 3.20 的报告标识为 beta.6/code106，只有 UI 和日志导出事件，缺少拍摄阶段记录。照片中的“未正确完成写入存储卡，要修复数据吗”来自 Sony 原生系统。当前无法由该报告确定先发生保存失败还是应用异常退出。

beta.6 的 25 秒超时分支会清理显影动画，API10 的 `Canvas.setBitmap(null)` 崩溃已在 rc.4 修复。rc.5 保留 PR #2 原始贡献，不把这一修复等同于原生写卡故障已定位。

代码检查确认，rc.4 的保存观察线程可能在 `storeImage` 尚未返回时扫描 DCIM、读取 JPEG；它先检查文件完整性，之后才查 Sony 索引。索尼 SD 日志导出的既有设备证据显示，同一文件写入端未关闭时读端可能收到 EBUSY。因此 rc.5 调整调用顺序，减少与原生保存并行的文件访问。这里的读写冲突是修复依据，尚没有 A7 现场证据将其确定为原生修复提示的唯一原因。

## 新链路

1. 提交保存前取得索引最新 `rec_order`，建立本次水位和持有记录。
2. 等待本次 RPC 真正返回。尚未提交或正在调用时，轮询不查询索引、不打开 JPEG；超时不释放资源、不重复提交。
3. 查询 `rec_order > 水位`，按倒序最多读取两行。没有记录则继续等待，多条记录保留歧义错误。
4. 按唯一记录的 DCF 目录号/文件号定位目标。匹配的具名通知可直接提供路径；丢失或错误通知只需定位对应目录并检查文件名，不逐张访问旧照片。缓存已定位路径，产品启动不建立全 DCIM 快照。
5. 两次元数据采样稳定后检查完整 JPEG 和尺寸。未写完且元数据不变时，完整内容检查最多每秒一次；即使 FAT 时间戳和长度未变化，后续仍可恢复。
6. 确认只完成一次，再进行调色/下一次保存或停止清理。原片与成片分别建立水位，保留既有跨进程防重入。

`CAPTURE.WAIT` 新增确认阶段、索引查询次数/累计耗时和文件检查次数/累计耗时。拍摄进程主动结束与 Java 未捕获异常转交系统前显式关闭诊断写入端，避免仅依赖进程终止收尾。

## 验证

- 主机 24 MiB：16 组现代/旧协议、12–42MP 链路；4 组实际阻塞线程 × 继续/停止，以及跨进程持有记录。
- 新增真实文件夹故障测试：索引缺失时移走 DCIM 仍可安全等待；300 个干扰文件、反向修改时间、错误通知、索引先于文件、部分 JPEG、同长度/同时间戳补写、DCF 重号，以及目标改变后失败不得复用旧缓存。
- API10 ARM 模拟器 / 24 MiB：同一安装 APK 运行上述链路与索引套件，另含原有 30 组初始化和 96 轮 Bitmap/Canvas 清理。
- 发行 APK 保持现有签名与完整 LUT/原生像素资源，检查 API10、DEX035、ARMv5/v7、v1 签名及发行资源边界。

执行入口：`scripts/test_product_ui.sh`、`scripts/test_capture_pipeline.sh`、`scripts/build_android.sh --release`、`scripts/test_legacy_emulator.sh emulator-5580`。本地原始输出保存于忽略目录 `results/indexed-store-20261102/`。

本版没有连接或安装真实相机，未模拟实体快门。若 Sony 保存服务永久不返回，保留原会话与持有记录；不能用线程中断或并发释放安全地取消这一调用。
